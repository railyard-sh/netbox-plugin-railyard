# netbox-plugin-railyard

A [NetBox](https://netbox.dev) plugin that connects NetBox with **[Railyard](https://railyard.sh)**, the
data-centre design tool, in both directions:

- **Sync from Railyard** (Railyard → NetBox): reconcile a Railyard estate into NetBox — sites, locations,
  racks, device types, devices, ports and cables — so the design becomes real DCIM data without a manual CSV
  import. It uses [DiffSync](https://github.com/networktocode/diffsync) and only ever changes what it created.
- **Import into Railyard** (NetBox → Railyard): bring NetBox sites into Railyard as a design baseline, and
  refresh that baseline later without losing what was designed in Railyard. NetBox is only read.

Both run as native NetBox background Jobs, with a dry run by default. The Railyard side (API client, the sync
document reader, the importer, the ownership tag) is the shared
[`railyard-sync`](https://github.com/railyard-sh/railyard-sync) package, so the plugin and the `railyard-sync`
command line behave identically and recognise each other's work.

> [!WARNING]
> **Pre-1.0 software that writes to your NetBox. Back up your NetBox database before every sync.**
> Run a **dry run** first and read its job log before applying anything, and try it on a copy of your
> NetBox before pointing it at production. The plugin is provided under the Apache-2.0 licence
> **without warranty** (see [LICENSE](LICENSE)).

> Status: **early development (0.2).** Both jobs have an integration suite that runs against NetBox 4.5, 4.6
> and 4.7 — see [Development](#development) and the [Roadmap](#roadmap).

## How it works

```
Sync from Railyard (Railyard → NetBox)
  Railyard: NetBox sync document ──► SyncDocumentAdapter (source) ─┐
                                                                    ├─► DiffSync diff ─► create/update[/delete]
  NetBox ORM (objects the sync owns) ─► NetBoxAdapter (target) ────┘

Import into Railyard (NetBox → Railyard)
  NetBox ORM (chosen sites) ─► Snapshot ─► Railyard project ─► new estate, or merged into the existing one
```

### Sync from Railyard

- Railyard is the **source of truth**. The source is Railyard's **NetBox sync document**: the objects of
  Railyard's own NetBox export, generated by the Railyard server for this NetBox's release (4.5 and later map
  front ports to rear ports differently, and the component types differ by release). The plugin no longer
  re-implements Railyard's export: names, slugs, statuses and the cabling plan are Railyard's.
- **The sync document is a paid deliverable on hosted Railyard** (railyard.sh). The estate's plan must include
  deliverables, and its rack count must be within the plan's deliverable limit. When it isn't, Railyard refuses
  with HTTP 402 and the job fails with the upgrade message, for example: *Exporting to NetBox needs a plan with
  deliverables: the Community plan does not include them. Upgrade to Pro or Team, or buy a Project Pass for
  this estate. Nothing was written to NetBox.* A **self-hosted Railyard with billing off** serves it to every
  estate.
- Default is **create/update only**. An explicit **"Allow deletes"** option also removes objects *the sync
  created* that are no longer in Railyard; without it they are listed as stale.
- A **dry run** (the default) only reads NetBox: it writes nothing, not even the ownership tag, and lists
  what a real run would create, update, rename, delete, skip and keep.
- A real run is **all or nothing**: it applies every change in one database transaction, so if anything
  fails, nothing is changed. Every change appears in NetBox's changelog under the user who ran the sync.

#### What the sync will and won't touch

Every object the sync creates is tagged with its project's **ownership tag**, named
`RY:<project name> (<id>)`. The tag is specific to one Railyard project on one Railyard instance (it is keyed
by the project's id, not its name), and the sync recognises it by its exact description. The
`railyard-sync export netbox` command uses the same tag, so the plugin and the command line can sync the same
NetBox (give both the same Railyard URL).

- **It only ever updates or deletes objects that carry its ownership tag.** It finds them by NetBox id and
  tag, never by name.
- **It never takes over objects you created.** If NetBox already has a manufacturer, device type, role, site,
  location or rack with the same name, the sync *uses* it (for example, it places its devices in your
  existing rack) but never tags, changes or deletes it.
- **Conflicts are skipped and reported.** If your NetBox already has a device with the same name in the same
  site, the sync doesn't touch it; it skips that device, its ports and cables, and lists them in the job log.
  The same applies to a port that is already cabled, and to a device type whose slug another type uses.
- **One exception: components of a device the sync created.** When the sync creates a device whose device
  type has component templates, NetBox creates those components too. The sync adopts (tags) the ones its
  design uses, and the job log lists them.
- **Deletes (opt-in) never reach beyond what the sync owns.** An owned object is kept, and reported, if
  deleting it would also delete or change something the sync doesn't own (for example your device in its
  rack, or your cable on its port). Deleting an owned device removes its components with it, as NetBox
  always does.
- If you remove the ownership tag from an object, the sync stops managing it.

Devices carry a `railyard_id` custom field (the Railyard placement id). A device **renamed in Railyard is
renamed in place** in NetBox — same NetBox object, components, cables and history — unless the new name is
taken in the site, which is reported as a conflict. Design tags on racks and devices are created in NetBox
when missing and follow Railyard on owned objects; serials, comments, cable types, statuses and colours do too.

#### Device types

The sync document names each device type and its Railyard catalogue key, which is the
[netbox-community device-type library](https://github.com/netbox-community/devicetype-library) slug. A
device type NetBox doesn't have yet is created **lean** (manufacturer, model, slug, height, depth, part
number); the sync creates exactly the ports its cabling needs. With `import_components` on, new types also get
the library's component templates, fetched at a **pinned library commit**. An existing device type with the
same manufacturer and model is used as it is.

### Import into Railyard

The import reads the chosen sites from NetBox's own database — the same fields, units and port mappings the
`railyard-sync import netbox` command reads over the REST API (the integration suite checks both read the same
NetBox into the same snapshot) — and runs railyard-sync's import:

- **A new estate**: regions and locations become spaces, then racks, device types (matched to Railyard's
  catalogue by their device-type-library slug, otherwise built from NetBox's templates), racked and 0U devices
  with their real ports and power inlets, data cables, and power cables to PDU outlets. Power feeds set each
  rack's power capacity.
- **A refresh** of an estate imported before: every imported object has an id derived from its NetBox id, so
  the import is merged into the estate. What was designed in Railyard is kept; objects deleted in NetBox are
  reported as stale, and removed only with **Allow deletes** (never when a Railyard object depends on them).
  An estate imported from another NetBox, or from more sites than this import reads, is refused. The estate is
  saved with the revision it was merged into, so a change made in Railyard meanwhile is never overwritten.
- **Honest about gaps**: unracked and child devices, modules, console ports, circuits, power panels and feeds
  are not modelled by Railyard; the job log lists what was left out and why.
- **Checks first**: Railyard's own check of the document runs before the save; errors stop it. Conflicts
  between the Railyard design and NetBox (a Railyard device now overlapping an imported one) stop it too.
- **Plan limits apply**: Railyard caps racks per estate by plan (Community 25). An import past the cap is
  refused with the upgrade message; it never imports part of a site silently.
- A **dry run** (the default) shows the import report, the re-import changes and Railyard's check, and saves
  nothing. NetBox is never written by the import.

The estate records this NetBox's address as its source (the URL the form was used on, or `netbox_url`); an
estate imported by the plugin can be refreshed by `railyard-sync import netbox` with the same URL, and the
other way round.

## Architecture

| Path | What | NetBox import? |
|---|---|---|
| [`railyard-sync`](https://github.com/railyard-sh/railyard-sync) (dependency) | Railyard API client, sync-document source adapter, canonical DiffSync models, importer, ownership tag, plan messages | **No** — shared with the `railyard-sync` CLI and the future Nautobot app |
| `netbox_railyard/policy.py` | Permissions per job, org/project allowlist, token loading | **No** — unit-tested here |
| `netbox_railyard/target.py`, `devicetypes.py` | **Sync target** — ORM adapter + create/update/delete + ownership rules (the REST twin is `railyard_sync.export.netbox_rest`) | Yes |
| `netbox_railyard/loader.py` | **Import source** — reads NetBox's ORM into a railyard-sync `Snapshot` | Yes |
| `netbox_railyard/jobs.py`, `import_job.py` | The two `JobRunner`s | Yes |
| `netbox_railyard/forms.py`, `views.py`, `navigation.py`, `templates/` | Trigger forms and the sidebar entries | Yes |

## Install

`railyard-sync` is not on PyPI yet, so it is installed from GitHub, pinned to a commit, as a dependency of the
plugin. Installing the plugin installs it (pip needs `git` for that):

```bash
pip install netbox-plugin-railyard        # (once published)
# or, from a checkout, into the NetBox virtualenv:
pip install -e /opt/netbox-plugin-railyard
```

Without `git` on the NetBox host (the netbox-docker image, say), install railyard-sync first from a
source archive, then the plugin without dependencies:

```bash
pip install https://github.com/railyard-sh/railyard-sync/archive/<commit in pyproject.toml>.tar.gz
pip install --no-deps /opt/netbox-plugin-railyard
```

Enable it in `configuration.py`:

```python
PLUGINS = ["netbox_railyard"]

PLUGINS_CONFIG = {
    "netbox_railyard": {
        "railyard_url": "https://railyard.sh",  # your Railyard base URL (use https)
        # The token: prefer a file (e.g. a mounted secret) to putting it in configuration.py.
        "railyard_token_file": "/run/secrets/railyard_token",
        # "railyard_token": "ry_...",
        # Which Railyard organisations and projects the jobs may reach. Users pick from these; nothing
        # else is reachable. With none configured, only the token user's personal org is used.
        "railyard_org": "my-org",  # the default org (id, slug or name)
        "railyard_allowed_orgs": [],  # further orgs users may choose
        "railyard_allowed_projects": [],  # optional: only these project ids/slugs (sync, and import refreshes)
        # This NetBox's address, recorded as an import's source. Default: the URL the import form was used on.
        # Set it when NetBox is reached under several names, so every import records the same one.
        # "netbox_url": "https://netbox.example.com",
        # Give device types the sync creates the device-type library's component templates (default off).
        # "import_components": False,
        # Device-type library commit; defaults to a pinned SHA. Override only after reviewing upstream.
        # "devicetype_library_ref": "<40-character commit SHA>",
    },
}
```

Requires **NetBox 4.5, 4.6 or 4.7** (Python 3.12+). The plugin refuses to load on other releases until it has
been tested with them.

### The Railyard token: least privilege, expiry and rotation

Every job uses the one token configured here, whichever NetBox user runs it, and it can read **everything its
Railyard user can see**. Railyard tokens aren't scoped yet, so limit what that user can see:

1. **Use a dedicated Railyard user for the plugin**, not a person's account.
2. **Give it the least role that works, only in the organisations it needs.** The sync only reads from
   Railyard, so for the sync alone use the *viewer* role. The **import writes estates**, so it needs the
   *editor* role in the organisations you import into; use the import only if you are content for NetBox
   users with the import permissions to write there.
3. Create its token under **User settings → Personal access tokens**. Tokens **expire** (90 days by default,
   7–365 days if you choose); choose the shortest expiry you are prepared to rotate.
4. Store it in a file readable only by NetBox (`railyard_token_file`), not in `configuration.py` or in
   version control.
5. **Rotate it before it expires.** Create a new token, replace the file, then revoke the old token in
   Railyard. NetBox reads the token at the start of each job, so no restart is needed for
   `railyard_token_file`.

Also set `railyard_org` / `railyard_allowed_orgs` (and, if you like, `railyard_allowed_projects`), so that
only the orgs and projects you choose can be reached, even if the token's user can see others.

If the token is wrong, revoked or **expired**, Railyard returns HTTP 401 and the job fails with a message
saying so. Rotate the token as above. A 403 means the token works but its user can't read (or, for an import,
write) that org or project.

### NetBox permissions

Both jobs use NetBox's own permissions. **Each job re-checks them** when it runs, and applies object-level
constraints to every object it reads or writes.

| To… | the user needs |
|---|---|
| open the sync page and run a **sync dry run** | `view` on manufacturer, device type, device role, site, location, rack, device, interface, front port, rear port, port mapping, power outlet, power port and cable, plus `extras.view_tag` |
| **apply** a sync | the above, plus `add` and `change` on the same DCIM models |
| apply with **Allow deletes** | the above, plus `delete` on the same DCIM models |
| run the **first** sync of a project | `extras.add_tag` (for the ownership tag and any design tags); the very first sync on a NetBox also needs `extras.add_customfield` and `extras.change_customfield` (for `railyard_id`). An administrator can run that first sync. |
| open the import page and run an **import** (dry run or real) | `view` on region, site, location, rack type, rack, manufacturer, device type, device role, device, the interface/front port/rear port/power port/power outlet/console port templates, those components, port mapping, cable, power panel and power feed. What the user may not view is not imported. |

## Usage

### Sync from Railyard

1. **Back up NetBox.**
2. Open **Plugins → Railyard → Sync from Railyard**, pick the organisation and project, and run a **dry run**
   (ticked by default).
3. Read the job log: what would be created, updated, renamed and deleted; existing objects it would use as
   they are; what it would skip because it doesn't own it; and deletes it would refuse.
4. To apply, untick *Dry run*, tick *Allow deletes* only if you want a mirror, and confirm that you've
   reviewed the dry run and backed up NetBox.

### Import into Railyard

1. Open **Plugins → Railyard → Import into Railyard**.
2. Choose the sites (or tick *All sites*) and the organisation, then either a name for a **new estate** or the
   id or URL slug of the **estate to refresh**.
3. Run a **dry run** first (ticked by default): the job log shows what was read, what the import leaves out,
   the changes a refresh makes, and Railyard's check.
4. Untick *Dry run* to save. Tick *Allow deletes* only to remove imported objects that are gone from NetBox.

Each run is a native NetBox background Job; watch progress and the log on the Job detail page.

## Upgrading

### From 0.1.x to 0.2

- **Install railyard-sync.** The plugin's Railyard side moved into the `railyard-sync` package; installing the
  plugin installs it (see [Install](#install)).
- **NetBox 4.5 to 4.7.** 0.2 needs NetBox 4.5 or later (it writes front-to-rear port couplings as NetBox 4.5's
  port mappings).
- **The sync reads Railyard's NetBox sync document.** It is generated by the Railyard server, so a Railyard
  instance must serve `POST /api/projects/{id}/deliverables/netbox-sync`; on hosted Railyard it is a paid
  deliverable (see above). What the sync creates now matches Railyard's own NetBox export exactly:
  - **Locations** are created for Railyard's spaces below a site, and racks and devices are placed in them.
  - **Slugs** of sites and locations carry Railyard's short suffix; the first 0.2 sync updates the slugs of
    objects the sync owns.
  - **Cable labels** are Railyard's. 0.1 made up a label for unlabelled cables
    (`SW-1:Eth1 <-> SRV-1:iface1`); 0.2 clears those on owned cables. Cable types, statuses and colours follow
    Railyard.
  - Serials, comments and design tags are synced, and **renamed devices are renamed in place**.
- **New permission**: the sync also needs the permissions above on `dcim.location`.
- **New job**: *Import into Railyard*, with its own permissions.

### From 0.1 (before the ownership tag)

- **Ownership tag.** 0.1 tagged objects `RY:<project name>` (slug `ry-<project-name>`). Objects with that tag
  are **no longer recognised**: the sync won't update or delete them, and it reports same-named devices as
  conflicts. To hand them over, run a dry run. Its log prints the new tag's slug, name and description. Edit
  the old tag in NetBox to exactly those values, then sync.
- **Organisation** is no longer free text. Configure `railyard_org` and/or `railyard_allowed_orgs` (and
  optionally `railyard_allowed_projects`). Without them, only the token user's personal org can be reached.
- **Permissions.** Users need the NetBox permissions above to open and run a job.
- **Adoption.** Existing objects are no longer silently tagged and taken over (see
  [What the sync will and won't touch](#what-the-sync-will-and-wont-touch)).
- **Device-type library** defaults to a pinned commit instead of `master`.
- Applying a sync needs the form's confirmation tick.

## Development

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"   # installs railyard-sync from GitHub at the pinned commit
pytest                    # the NetBox-free suite (policy)
ruff check .
```

The Railyard side is tested in [railyard-sync](https://github.com/railyard-sh/railyard-sync). To work on both
at once, install a local checkout over the pinned one: `pip install -e ../railyard-sync`.

`tests/integration/` exercises the NetBox side — permissions, ownership, dry runs, renames, the allowlist, the
plan refusals, and the import (the ORM reader reads the same snapshot as railyard-sync's REST loader; dry run,
create, refresh, conflicts) — against a real NetBox and PostgreSQL, under NetBox's test runner:

```bash
NETBOX_DIR=/path/to/netbox ./dev/run-integration-tests.sh
```

See the script for what `NETBOX_DIR` needs; CI runs it against NetBox 4.5, 4.6 and 4.7. The sync documents
the suite serves are written by Railyard's own exporter: `tests/fixtures/sync/make_documents.py` regenerates
them. For a clickable local NetBox, use [`dev/setup.sh`](dev/README.md).
